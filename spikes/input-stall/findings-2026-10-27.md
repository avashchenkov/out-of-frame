# Input stalls after a reply that should complete it

Question: how can the agent say it is ready, then keep waiting for the user?

## Evidence and limits

The reported conversation was not saved. The exact extraction and geocoding results are
unknown. This analysis identifies a failure path in the current code, not which field was
wrong in that live run. No model, live source or Docker calls are needed for this spike.

The relevant path is in `src/out_of_frame/agent.py` and `conversation.py`:

1. `extract_input` applies structured changes from one model call.
2. Code geocodes the addresses and computes what is missing.
3. If something is missing, `ask_for_missing` makes a separate model call to write a question.
4. Every accepted answer from that call goes to `wait_for_answer`, even a promise to start.

The question model cannot change the input or start research. Its output is checked only
for a normal stop reason and nonempty text. Its prompt includes the whole conversation,
which can appear complete even while the supplied missing fields say otherwise.

For destinations, `null` means no change in an extraction and not answered in the state.
`[]` means the user travels nowhere. The extraction prompt and schema already describe this
distinction. The prompt also already tells the model to resolve a choice among offered
addresses to the offered address text.

An extraction that misses either part of a combined reply leaves input incomplete. An
extraction that gets both parts right can still leave the property unresolved if geocoding
does not find one precise match. A readiness statement from the question call hides either
problem. The next reply, such as "Start then", adds no data; the extraction is instructed to
extract changes from the last message, so another empty change can keep the loop going.

## Offline reproduction

`reproduce.py` uses the real input graph, extraction parsing, state updates, geocoding and
pause/resume path. Model responses are supplied deliberately; Nominatim responses come from
existing fixtures. Execution stops before research. It compares:

- Both changes applied: the selected address resolves, destinations become `[]`, and research
  is next without a readiness message or another user reply.
- Commute answer omitted: destinations remain `null`; a supplied readiness statement is
  accepted and the graph waits again after "Start then".
- Address choice omitted: destinations become `[]`, but the address remains ambiguous; the
  same readiness statement and repeat pause occur.

This establishes the consequences of faulty model output, not its probability or whether
the live model would produce that output on these synthetic messages.

Checked on 2026-10-27:

- `uv run --offline --no-sync python spikes/input-stall/reproduce.py`: all three cases
  produced the expected outcome. Complete input scheduled `get_map_objects`, `get_plans`
  and `plan_journeys`. Both injected failures stayed at `wait_for_answer`, including after
  the extra start request, with the readiness statement as the interrupt text.
- `uv run --offline --no-sync pytest -q tests/test_conversation.py tests/test_geocoding.py
  tests/test_agent.py tests/test_service_graph.py`: 76 passed. These tests verify code with
  model stubs; they do not show that the live model follows either prompt.

## Proposed fix and checks

Prepare fixed input-loop cases before changing prompts:

| Case | Success criterion |
| --- | --- |
| Ambiguous address; one reply selects a candidate and declines regular travel | The selected building and `destinations: []`; research next on that turn |
| Resolved address; a later reply declines regular travel | `destinations: []`; no extra reply needed |
| Candidate selected; travel not answered | Address resolved; destinations remain `null`; a commute question |
| Travel declined; candidate not selected | Destinations empty; a question about the address |

Use unambiguous candidate names in the input-loop suite. Test ordinal choices such as "the
first one" with a fixed preceding assistant message, so free question ordering cannot change
the expected building. Keep the existing I1-I3 tasks as controls.

First change the two prompts, without changing who controls the graph:

- Extraction: explicitly process every answer in a combined reply; resolve an ordinal from
  the preceding offered list; an explicit no-travel answer must produce `[]` even when the
  same reply chooses an address. Keep unknown information unknown.
- Questions: define the role as writing a clarification for the supplied missing fields.
  That list is authoritative for this call. The model cannot update state, start research,
  declare readiness or ask for permission to start. If the conversation appears to answer a
  field that is still missing, ask a specific confirmation of that field.

Measure these changes with repeated model trials. Prompt changes reduce the risk but do not
guarantee semantic compliance. A separate question validator or fixed question templates are
larger changes; use them only if targeted evals still show readiness statements. Checking for
a question mark or a blacklist of phrases would not establish that a useful question was
asked. Never start research merely because a model said it was ready.

Proposed roadmap addition: stabilize input completion for combined answers, with the above
cases and existing input tasks as controls. This is a proposal, not a completed roadmap step.
